# Website playbook: how the Pluto site was designed and built

Written 2026-11-24 for the owner, who asked for "all the skills used, ideas, layouts, animations,
whatever the intelligence used to design the pluto website" in order to build other websites with
it. Every file named here is in this repository, so you can copy the code itself, not only the
ideas.

**What to copy, and what not to.** The method, the checks and the code structure carry over to any
site. The look does not: Pluto's planet, bear and colours belong to Pluto. A new site needs its own
story and its own one big visual idea. Copying the Pluto look onto a different product makes it
look like a template.

---

## 1. Skills (the "intelligence")

Claude Code skills are written guides that load into a session. Ask for them by name (for example
"use frontend-design") or type `/<name>`.

| Skill | What it did for Pluto | When to use it again |
|---|---|---|
| `frontend-design:frontend-design` | Choosing one bold direction (a real planet, sunrise to night) instead of a generic SaaS page; typography and composition | At the start of every site, before any code |
| `artifact-design` | Rules for pages shown in claude.ai previews: light and dark tokens, phone width, no outside scripts | Every preview you publish |
| `vectorlab-ux-skills:colour-palette` | 60-30-10 colour budget; one accent colour; 1px borders before shadows; dark mode lit at the edges, never glowing | Choosing colours and surfaces |
| `vectorlab-ux-skills:page-patterns` | Page structure: hero, proof, feature rows, final call to action | Planning the pages |
| `vectorlab-ux-skills:empty-states` | What a section shows before it has content | Any list, library or dashboard |
| `vectorlab-ux-skills:motion`, `reduced-motion`, `transitions` | Motion only where it explains something; every moving part has a still version | Before adding animation |
| `vectorlab-ux-skills:typography`, `spacing`, `surfaces`, `anti-slop`, `viewports`, `ux-audit` | Type scale, spacing rhythm, layers, removing "AI look" clichés, checking 360 to 1440 px, the final audit | Review pass before shipping |
| `dataviz` | The admin dashboard: chart choice, colour by job, a palette checked for colour blindness, tooltips, a table under every chart | Any chart or dashboard |
| `superpowers:systematic-debugging` | Finding root causes (for example an empty preview because the test data had no characters) instead of guessing | Whenever something breaks |

The website-design, animatedwebs and design-superpowers skills are installed too but were **not**
used on Pluto. Try them on the next site if you want a different starting point.

## 2. Research before design

- **Sites studied:** openpets.dev, Finch, Forest, Raycast, Things, Desktop Goose, typesafe.ai,
  jamm.co.
- **openpets.dev** (the closest competitor): we took its structure (a pet library and a
  try-it-now demo) and left its visuals.
- **Finch and Forest:** a character people care about sells a productivity tool better than a
  feature list does.
- **Raycast and Things:** calm, exact screenshots of the real app; no fake mockups.
- **Desktop Goose:** a pet that lives on the page itself is the demo.
- **The rule:** write down what each reference does well, in one line, before you open an editor.
  Then use ideas, never assets.

## 3. The story (layout of the home page)

The home page is one story, not a list of sections. Each scene answers the question the previous
one raised:

1. **Sunrise hero:** a live 3D Pluto at dawn with the bear standing on it, plus the headline and
   Download. It says what this is in one look.
2. **"Your day is everywhere":** scattered cards (tasks, timer, notes) gather into one window
   while you scroll. This is the problem and the fix, shown without words.
3. **Try it:** a live pet you can poke on the page. This is the proof.
4. **A day with Pluto, dawn to night:** a pinned scene; the sky and the app change through one
   day.
5. **Orbit:** Pluto turns while the five parts of the app circle it.
6. **Dress-up, then diary, then privacy:** the reasons people keep using it, and the trust
   question answered before anyone asks.
7. **Assistants, then Coming next, then the finale:** a night sky, the planet again, and the last
   Download button.

**To reuse:** write your own story as 6 to 10 one-line scenes first. If a scene doesn't move the
story forward, cut it.

The other pages are Features, Pet library (with the dressing room), Assistants, Pricing, Privacy,
Download and 404. They share one head, header and footer, generated by `scripts/site-pages.py`
(see section 7).

## 4. Visual system

- **Colour as tokens** (`website/styles.css`, top):
  - Every grey is tinted by one hue, `--gh`; the colour picker changes it.
  - Interactive things use one accent, `--accent`.
  - The colours are written in **oklch**, so the five themes (periwinkle, indigo, ultraviolet,
    amethyst, copper) have equal lightness and contrast.
  - The site wears the same five colours as the app (`src/lib/colours.ts`). The visitor's choice
    is kept in `localStorage` only.
- **Type:**
  - Two self-hosted variable fonts: Unbounded for display, Figtree for text. They are in
    `website/fonts/`, with their OFL licences.
  - No Google Fonts call, so visitors are not tracked.
  - Headings use `clamp()` sizes and `text-wrap: balance`.
- **Surfaces:** canvas `--ice`, raised `--frost`, 1px `--line` borders, and very soft two-layer
  shadows.
- **Layout:** `--max: 1160px`, gutter `clamp(16px, 4vw, 48px)`; everything is checked at 360,
  768, 1024 and 1440 px. On narrow screens the header becomes a menu button.

## 5. Animation techniques (all in `website/site.js`, `website/planet.js`, `website/styles.css`)

| Technique | How it works | Copy it from |
|---|---|---|
| **Scroll progress as a CSS variable** | One rAF-throttled scroll handler writes `--p` (0 to 1, how far an element is into view) on `[data-scroll]` elements; CSS does the rest with `calc()`, e.g. tilt `rotateX(calc((1 - var(--p)) * 26deg))`. No animation library. | `site.js` `onScroll()` |
| **Pinned scenes** | The section is 270vh tall with a sticky stage inside; progress through it (`--g`) drives the cards from scattered (`--sx`, `--sy`, `--sr` per card) to gathered. Text before and after cross-fades with `opacity: calc(...)`. | `.scatter` in `styles.css`, `scatterScene()` |
| **Reveal once** | `IntersectionObserver` adds `.in` to `[data-reveal]` the first time it is seen, then stops watching. | `site.js` |
| **Motion gating** | `site.js` adds `html.motion` only when the visitor has *not* asked for reduced motion. Every moving rule is written under `.motion`, so the default (no JS, or reduced motion) is a finished still page. | `styles.css` (comment at "Everything below that moves") |
| **Live WebGL planet** | One fragment shader, no library: it ray-traces two spheres (Pluto and Charon) and paints them with noise (fbm). Three scenes share it. It draws only while on screen, shows one still frame for reduced motion, and has a CSS-drawn fallback (`.no-gl`). | `website/planet.js` |
| **Sprite pets** | One shared clock steps every sprite sheet frame, so all pets move in time; rows are poses (idle, walk, wave, jump, type). | `sprite()`, `paint()` |
| **Pointer guide** | A small pet follows the mouse with easing and says context lines per section; it is on only for a fine pointer with no reduced motion, and a dock lets visitors switch it off. | `guide()` |
| **Dressing room** | The app's real outfit images, copied into `website/wardrobe/` by a test, placed using per-frame anchor points (`pets.json`, from `scripts/site-pets.py`). | `dressingRoom()`, `placeGear()` |
| **Hover card** | Hovering the pet shows the same card as the app. | `hoverCards()` |

**Timing rules used:** 120 ms for button feedback; 200 to 400 ms for entering elements; scroll
scenes are tied to scroll, not time. Nothing loops unless it is a living thing (the pet, the
planet).

## 6. Trust and speed

- No third-party requests at all: fonts, images and scripts are all on the site. `website/_headers`
  sets a strict Content-Security-Policy (`default-src 'self'`), `Referrer-Policy: no-referrer`,
  and turns off camera, microphone and location.
- Images are WebP; screenshots are of the real app (`website/shots/`).
- Animation pauses off-screen (WebGL and sprites).

## 7. Build and checks (why the site stays correct)

- **No build step for the site itself:** plain HTML, CSS and JS. `scripts/site-pages.py` writes
  every page from one head, header and footer plus a body in `scripts/site-pages/<name>.html`. The
  output is committed, so hosting is "upload the folder".
- **Tests check what the site claims against the code** (`src/website.test.ts`, 20 tests): the features, assistant support,
  diary, characters and their poses, colours, the user count and the "nothing loaded from other
  sites" promise must match the app and the code. The same tests check that every link and file
  exists and that reduced motion is respected. If the app
  changes, the test fails until the site is updated.
- **Assets come from the app by test** (`src/website.wardrobe.test.tsx`, run with
  `WRITE_SITE=1`), so the site never shows an outfit the app doesn't have.
- **Screens at four widths** with Playwright, looked at before every commit.

## 8. Recipe for your next site

1. Write the product in one sentence, and the visitor's one doubt.
2. Study 5 to 8 sites; one line each on what to take.
3. Pick one big visual idea that only this product could have (Pluto had a real planet).
4. Write the story as 6 to 10 scenes.
5. Set the tokens first: hue, accent, two fonts, surfaces, gutter, max width.
6. Build the still page completely (works with no JS and with reduced motion).
7. Add motion under `html.motion`: scroll variables, one pinned scene, reveals. Add WebGL only if
   the big idea needs it.
8. Add a `_headers` file with a strict CSP; self-host fonts.
9. Write tests for every claim the site makes about the product.
10. Screenshot at 360, 768, 1024 and 1440 px; run the ux-audit and anti-slop skills; fix; ship.

## 9. Hosting without a domain

- **Free hosting:** Cloudflare Pages (`<name>.pages.dev`), or GitHub Pages
  (`<user>.github.io`).
- **Free names** (from the community list at github.com/harys722/free-domains):
  - is-a.dev (developer pages, approved by GitHub pull request)
  - js.org (JavaScript projects only)
  - Open Domains (open-domains.net)
  - EU.org (a real free domain, approval takes weeks to months)
- Read each one's rules before using it for a product you sell.
- A product that takes payments should buy its own domain (about $10 a year) before launch. A
  free subdomain can be withdrawn, and it looks less trustworthy on a checkout page.
